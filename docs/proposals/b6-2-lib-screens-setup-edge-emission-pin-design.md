## 0. TL;DR

The evidence's central claims are **substantively accurate** — all nine citations resolve to the right symbols at HEAD `40acef7`; the two disclosed line drifts are real (`app_router.dart:35→:36`, `sso_client.dart` wire at `:98`); the census is in **constant mode** (`test/` literal ban enforced, exactly one `lib/` site), and `setup_screen_test.dart` is the only unpinned home for new widget tests. **Four additional inaccuracies** where the evidence claimed "Exact" were found and are corrected in §1 (harness capture line, already-initialized button location, stub getter line, drill SKIP lines), plus one byte-size mismatch (spec file is 23426 bytes, not 23020).

Two **design-critical discoveries** the evidence does not surface:

1. **REQ-3's setup leg has a precondition conflict with the device leg.** `POST /api/v1/setup` returns **409 already-initialized** on any live stack (`SetupResult.alreadyDone()` at `lib/api/setup_api.dart:98`; 409 mapping at `:208-209`). The device leg (steps 1-6) requires an *initialized* stack + `CONFIG` credentials; the setup leg requires an *uninitialized* stack. No single stack state satisfies both. The design keeps the leg unconditional and never-skipped, and instead makes the precondition a **hard check on `GET /api/v1/setup/status`** — the leg FAILs loudly (exit 1) on an initialized stack, with the deviation recorded in the drill's `[RESOLVED]` note. REQ-3's "Testable" claim ("passes once B4-5 lands on a deployed stack") is corrected: green is reachable only on a **fresh** stack with B4-5 landed.
2. **Sink-count coupling with steps 4/5.** Step 4 asserts `len(matching) == 1` and Step 5 asserts `len(rows_after) == 2` for the *device* tenant. The setup leg is only additive if it is **tenant-isolated**: fresh setup → new tenant → own JWT `tenant_id` → own `sink_rows` query — the fresh-tenant half is an **assumption** (external `sso-server` behavior; zero in-repo evidence, §1 D2), and §7(c) gates green on its verification. Same-tenant insertion would redden the untouched steps 4/5 (contradicting "additive"). The design makes this a hard constraint and uses **separate local variables** (`setup_token`/`setup_tenant_id`) so step 3's `token`/`tenant_id` are never clobbered.

Design is **test-only + one additive drill step**: 3 `testWidgets` in `test/setup_screen_test.dart` (4 → 7, unpinned), zero `lib/` changes, pinned suites untouched; the census-internal 43-count pin is unchanged, and the §7 joint command grows to **44** (43 + FG-3's 1 pre-existing call-site pin, count-unpinned — FM-4) → **51/51**.

## 2. Design

### 2.1 REQ-1 — Both post-wizard exits record `/admin/` (2 `testWidgets` in `test/setup_screen_test.dart`)

Both exits record the target **synchronously** into the stub: `assignLocation`/`replaceLocation` → `_replaceRoute` → `_currentUri = _parseLocation(location)` (`browser_navigation_stub.dart:35-36`) before the post-frame route replacement (which no-ops safely when `AppNavigator.key.currentState` is null in a bare `MaterialApp` — the `:40-41` guard). The existing `setUp` (`:13`) guarantees a clean `Uri.base`. Assert on the static getter, exactly like `entry_ux_test.dart:193,213`.

**Exit 1 — already-initialized panel → `assignLocation` (`setup_screen.dart:172`).** Fixture `{"setup_required":false}` (`:148` shape — the `:145` test's fixture); pump `SetupScreen(api: api)`; `pumpAndSettle`; `tap(find.text('Go to admin console'))` (the panel's single `FilledButton`, `setup_widgets.dart:55-58`); `expect(BrowserNavigation.currentUri.path, '/admin/')`. No wizard steps — minimal path.

**Exit 2 — done panel → `replaceLocation` (`setup_screen.dart:362`).** Walk the wizard with the no-secret fixture `{'created': {'admin': 'root'}}` (`:110` shape — the `:99` test's fixture; no `client_secret`, so the done action is enabled without the secret-saved checkbox, `setup_widgets.dart:355`): fill admin form (`'Admin username'`, `'Password'`, `'Confirm password'` — ≥8 chars), tap `'Continue'`, `pumpAndSettle`, tap `'Skip and finish'`, `pumpAndSettle`, tap `'Go to admin console'` (done panel's `FilledButton`, `setup_widgets.dart:354-358`), `expect(BrowserNavigation.currentUri.path, '/admin/')`.

Both: no `'sso-admin-console'` token anywhere (census), no skip tokens (convention §4).

### 2.2 REQ-2 — Setup-originated login wire carries the first-party client_id (1 `testWidgets` + file-private harness)

File-private `_SetupLoginHarness` — a faithful mirror of `_LoginHarness` (`oidc_login_screen_client_id_test.dart:27-104`): `MockClient` over `OidcLoginApi(baseUri: Uri.parse('https://sso.example/'), httpClient: …)`; credential-bearing `POST /auth/login` (D9 filter `body['credential'] is Map`, `:34`) → scripted `{'access_token': 't', 'session_id': 's'}` 200, captures `loginPosts`/`lastClientId`; probe/branding/anything-else → `{}` 404 treated as absence.

Pump with the **exact `app_router.dart:36` wiring expression**:

```dart

  api: api,
  defaultClientId: SSOAdminClient.firstPartyClientId, // the :36 expression
  routeUri: Uri.parse('https://sso.example/login/?redirect=/admin/'),

```

(`redirect` is inert per §1; `_effectiveClientId` falls back to `defaultClientId` since the URI carries no `client_id`.) Submit the admin form (Username/Password → tap the `FilledButton` `'Sign in'` — the hosted harness's `submit()` tap at `:101` (inside `submit()` `:89-103`)). Assert:

- `harness.lastClientId == SSOAdminClient.firstPartyClientId` — the wire value through `app_router.dart:36` → `_effectiveClientId` (`:159-161`) → `sso_client.dart:98`.

Scope discipline: **no `probePosts` assertion** — probe behavior is the hosted sibling's pin; this test pins the login wire only.

### 2.3 REQ-3 — Drill extension: setup-originated leg, exactly-one row, zero duplicates, zero matches → exit 1 (`[PROPOSED]` until B4-5)

New additive block **between Step 3 and Step 4**, banner `【3b. Setup-originated login leg (REQ-3; sink emission [proposed]: IdP-side B4-5, zero emission strings in this repo — census `:97-105`)】`. Steps 1-6 are letter-untouched (no renumbering). The leg uses **local variables only** (`setup_token`, `setup_tenant_id`, `setup_login_data`) — step 3's `token`/`tenant_id` (device leg, used by steps 4-6) are never written by this block.

Sequence (each a `check(...)` — a failed check flips `FAIL`, exit 1 at `:292`; **no `proposed` path inside the leg**). All drill line anchors in this section (and §7's drill citations) are **pre-insertion HEAD values**: landing the `【3b】` block shifts every anchor after Step 3 (Step-4 idiom `:182`, Step-5 mirror `:213-215`, `[RESOLVED]` note `:288-289`, exit `:292`) by the block's line count — re-pin those citations at landing time (nothing in §7(c) is post-insertion: `:78-82` and `setup_api.dart:161-162` precede the block):

1. **Stack freshness — hard precondition check.** `GET {PROXY}/api/v1/setup/status` → `check("setup leg: stack uninitialized (setup_required)", data.get('setup_required') == True, …)`. On an initialized stack this FAILs loudly (never a skip) and the deviation is recorded per the `[RESOLVED]` note convention (drill `:288` precedent; `docs/proposals/audit-contract-batch-snaplink-console.md`). This is the concrete resolution of discovery D1.
2. **Wizard completion wire.** `POST {PROXY}/api/v1/setup` with `{'admin': {'username': 'drill-setup-<epoch>', 'password': 'drill-pass-<epoch>'}}` (module wire `lib/api/setup_api.dart:161-162`; fresh username keeps the leg repeatable; password ≥8 chars per the wizard validation the `:17` test pins). Check `ok == true` and `created.admin` present. A **409** → `check(..., False, 'already initialized')` → FAIL (never routed into `proposed`).
3. **Immediate login.** Payload = `CONFIG.login_payload(password=created_password)` with `payload['credential']['username'] = created_admin` merged locally (discovery D3 — `test_config.py` untouched; `'client_id': self.client_id` carried from `:90`). `POST {PROXY}/auth/login`; decode the JWT (existing `decode_jwt` helper, Step-3 convention); `setup_tenant_id = claims.get('tenant_id')`; missing claim → FAIL (B4-1 dependency, same as Step 3). Print the **D2 premise-evidence line** — `setup_tenant_id` alongside the device leg's `tenant_id` — for the `[RESOLVED]` note; the premise ("fresh setup → fresh tenant") is **not** assumed green, and this output is the empirical channel for §7(c)'s gate (see §1 D2, FM-17).
4. **Settle ingestion — before the first query** (F11). `settle = settle_seconds()` (`:71-74` — `max(10, SNAPLINK_DRILL_SETTLE_SECONDS)`) + `time.sleep(settle)`, the same ingestion-lag budget the device leg applies (Step 5 at `:202-204`, Step 6 at `:247-249`). The setup login is *immediate* (API-driven, no browser round-trip to mask lag), so the first query must not race the sink: on a healthy post-B4-5 fresh stack the settle makes `len(matching) == 1` deterministic; on a B4-5-absent stack zero matches still FAIL **after** the settle (loud, never skipped); a slow stack raises the budget via the env knob without editing the file.
5. **Sink query — tenant-isolated** (discovery D2, **valid only under the §1 D2 assumption**). `sink_rows(setup_token, setup_tenant_id)` (builder `:78-82`, same `event_types=auth.login.success&tenant_id=` shape); filter `r.get('client_id') == AGREED_CLIENT_ID` (Step-4 idiom `:182`). If the server seeds the initial admin into a shared/default tenant, this query silently collides with the device tenant and untouched steps 4/5 redden — the premise gate (FM-17, §7(c)) is what keeps that outcome from ever being accepted as green.
6. **Hard checks** (mirror of Step 4's semantics — unconditional):
   - `check("setup leg: exactly one auth.login.success row with client_id=<AGREED>", len(matching) == 1, …)` — **zero matches is a FAIL → exit 1, never a skip, never a PASS**; duplicates also FAIL;
   - re-settle (`settle_seconds()`) → re-query → `check("setup leg: count stable after re-settle", len(rows_after) == len(matching), …)` — pins 无重复 over ingestion lag (mirror of Step 5 `:213-215`).
   - `rows is None` (sink unverifiable) → FAIL (unlike the device leg's Step-4 `proposed` convention, this leg has no proposed path — per the direction's never-skip rule; a runnable leg never converts a zero/unverifiable result into `proposed`).

- **`redirect` query inertness**: REQ-2's `routeUri` with `?redirect=/admin/` must not grow a `client_id` param (that would switch `_effectiveClientId` off the fallback and the test would still pass for the wrong reason); `redirect` itself is ignored by `OAuthParams`.
- **B4-5 dependency**: the sink row is IdP-emitted (deployment repo); this repo's census pins zero emission strings (`:97-105`). REQ-3 goes green only after B4-5 lands **and** on a fresh stack; before that it fails loud (exit 1) — the intended gate for `implementation-gate.md:57`, never converted to a skip.

## 8. Risks and scope exclusions

- **Scope exclusions (unchanged)**: `test/entry_ux_test.dart` (10-pin, B6-2 device group), `test/oidc_login_screen_client_id_test.dart` (3-pin), `test/sso_client_test.dart` (17-pin), `test/sso_client_login_exactly_once_test.dart` (3-pin), the census file (10-pin), all `lib/` production, the IdP-side emission (B4-5, deployment repo), the device-leg drill steps 1-6.
- **Risk — setup leg red on initialized stacks (inherent to the acceptance)**: the setup wizard is a one-time bootstrap; the acceptance `implementation-gate.md:57` setup-originated path is exercisable only at first deployment. The design converts this from a silent hazard into an explicit check (D1) + `[RESOLVED]` record; the alternative (auto-skip) contradicts the direction's never-skip rule.
- **Risk — CI-latency exposure of the REQ-3 leg (latent today; live the moment the drill is CI-wired)**: CI's fixture credentials are `admin`/`admin` (`.github/workflows/ci.yml:87-88`, pinned by `tests/unit/test_deployment_contracts.py:268-269`) — they imply a live **initialized** stack in CI's integration environment. At HEAD the drill is unreachable from CI: `make integration` → `full_integration_test.py` (zero drill references; `ci.yml:89`), and the drill's only invocations are `run_all.py:169` (E2E section, executed only when neither `--skip-e2e` nor `--ci` is set) and `full_stack_verify.py:113` (manual `make full-stack`). If anyone wires the drill into CI (a `run_all.py` call without `--ci`, or a full-stack step added to `ci.yml`), the new leg's freshness pre-check FAILs on that initialized stack → exit 1 → CI red on every run. The fix, when that day comes, is a CI-mode exclusion for the setup leg mirroring `run_all.py`'s `--ci` semantics; today the exposure is inert (D4).
- **Risk — tenant-isolation regression**: if a future edit reuses step-3's `token`/`tenant_id` in the setup leg, untouched steps 4/5 redden — the loudest possible signal; no silent path.
- **Risk — FM-7 (silencing not enforced on the unpinned file)**: documented; the natural fix is widening the census ban list to include `setup_screen_test.dart` in a future census amendment — deliberately not in this direction's scope (census file is pinned). The same class now covers FG-3's 1 test in the joint command: deletion/skip silently shrinks 51→50 with exit 0 — count-unpinned by design (no gate references the file), so only the census-literal scan guards it.
- **Risk — drill-in-CI latent exposure (carried from review)**: CI fixture creds (`admin`/`admin`, `ci.yml`) imply an initialized stack; the drill is today reachable only via `run_all.py` (skipped under `--ci`) and `full_stack_verify.py` (manual), so the REQ-3 leg's exit-1-on-initialized-stack behavior is inert. Wiring the drill into CI without a fresh stack would redden that job — the intended loud signal, but confirm stack state before any such wiring.
- **Risk — byte-size/citation drift in the evidence**: all corrected in §1; no design decision depends on a line number (assertions reference symbols and the constant).
